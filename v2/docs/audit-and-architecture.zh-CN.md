# NetFlow Plus V2：数据源审计与架构基线

审计日期：2026-11-19（北京时间）。仅只读检查；未修改现有 DNS、路由器、容器或历史数据库。

## 实际环境

- OxiDNS 1.7.1 full 作为独立进程运行，管理 API 监听 `192.0.2.4:9199`，DNS 监听 53；query_recorder 功能已编译并使用独立 SQLite。查询记录可能包含代理或转发来源，来源 IP 数不代表独立设备数。
- 记录主表包含 `id`、`created_at_ms`、`client_ip`、应答数量和压缩 payload，查询名存于关联 question 集合；不能把 SQLite payload 当成明文 JSON。库含两种 payload codec。不得直接改写、解压回写或对运行中的库执行迁移。
- 管理 API 返回 HTTP 401 和 `Basic realm="oxidns"`。公开文档描述 query_recorder records 列表支持 cursor、时间过滤，并返回 questions、answers、TTL 和 IP；受认证限制，此次没有取得真实认证响应，实际标签名、权限与字段兼容性仍需在用户配置凭据后验证。参见 https://oxidns.org/en/api/plugins/ 和 https://oxidns.org/en/plugin-reference/executor/observability/ 。

后续使用 OpsMaxx 在 OxiDNS 主机上做了认证只读核验，未输出凭据或查询内容：响应的顶层、记录、question 和 answer 字段类型与当前客户端一致。一个距当前约三分钟、长度十分钟的固定历史窗口中，API 共 6 页、2748 条，与 SQLite 相同窗口的记录 ID 集合完全一致。另取最近 500 条记录检查了 A、CNAME 等应答和 TTL 字段。此抽样不构成所有时间窗口都完整的保证，服务离线、迟写、DNS 缓存及 DoH 等仍可能造成缺口。
- 已运行的 NetFlow Plus 为 `admbb99/netflow-plus-zh:latest`，包含 `/api/v1/devices`、`/api/v1/flows`、`/api/v1/overview`。带密码部署采用登录 Cookie 或 HTTP Basic；不能假设存在 API key。
- `/api/v1/flows` 每页最大 1000、按连接时间范围相交筛选；上/下行是连接累计值而非查询窗口内增量，低于 foldBelow 的连接可能被折叠。轮询快照必须处理累计量变化、连接重置、分页排序变化、丢页和重启；不能将累计值直接汇总为所选时段真实流量。原有 rollup 的总量更完整，但不含可安全重构每条连接 DNS 证据的维度。
- 源项目已存在 19 条启用的内置域名规则、用户规则与 Simple Icons 依赖；只应复用并保留来源和许可，不复制全量泛 CDN 规则作应用识别。

## V2 独立边界

独立目录、独立 SQLite、独立端口和数据卷；通过只读 HTTP 访问现有服务，不更改 RouterOS、OxiDNS 配置或现有数据卷。API 身份凭据通过环境或 Docker secrets 配置，不写入日志、URL、镜像或源码。管理 API 优先使用 HTTPS 或受信任网络，Basic 凭据不应跨不受信任网络明文传输。

OxiDNS 数据应按时间窗口和 cursor 增量获取；cursor 倒序、分页和并发新增记录必须采用固定上界、完全翻页、ID 去重及事务提交 checkpoint。只在完整区间成功落库后推进，失败保持旧 checkpoint。DNS 查询统计仅叫查询次数，不等同流量。统计接口如使用源侧 top 接口，必须检查其采样/截断提示。

DNS/IP 匹配必须满足同一个客户端、目的 IP、DNS 时间早于流开始、30/60/120 秒窗口、每条 CNAME 与 A/AAAA TTL 有效；同一条件下多个应用或未知候选同时存在时保留 unknown。即使条件满足也属于推断，并非逐包证明。DoH、系统缓存、代理、共享地址以及源数据缺失均可能造成漏识别或错误关联。记录匹配规则、来源、DNS 事件 ID 和原因；只接受可信 DNS 回答链。

流量必须采用幂等增量及不可变时间桶，识别不充分的字节归 unknown，不能从 DNS 查询次数推算字节。由于当前 NetFlow API 仅暴露连接快照与聚合，尚未证明能够在外部独立服务准确恢复所有分钟流量；在接口能力或只读数据契约验证之前不得标为完整真实排行。

## 首轮实现和待办（历史记录）

已创建独立 Go 模块，包含保守 DNS 证据匹配、冲突/TTL/CNAME 单元测试，以及基于公开文档的 OxiDNS Basic 只读分页客户端和 HTTP fixture 测试。客户端尚未对真实认证记录验证，不具备持久化或调度；关联算法尚未接入流量或 Web 页面。

尚未实现：真实增量同步、抗乱序与多实例故障恢复、NetFlow 适配器、数据表迁移与聚合、用户规则和图标管理、REST/HA API、React 仪表盘、Docker 构建、线上联调、完整应用规则及许可证复核。当前目录不是可部署成品，不应发布或宣传为 V2 完成。

## 第二轮实现进度（历史记录）

新增独立 SQLite `dns_events` 和 `sync_state`，按来源与记录 ID 幂等保存；同一 ID 对应不同内容时停止同步。分页固定区间、失败重试不推进 checkpoint，重复 cursor 和超页数失败；单页使用事务。证据查询按客户端和时间筛选，超限返回错误而非截断；分析前要求 DNS 同步进度覆盖连接开始时间。新增 OxiDNS 记录到证据转换，以及同步、ID 冲突、截断、TTL、共享 IP、API 鉴权和关联集成测试。

仍需在真实认证环境验证响应结构、DNS 写入延迟与完整性；checkpoint 只是客户端已完成拉取的进度，并不构成上游异步写入已经完全落盘的证明。需要明确延迟缓冲与重扫策略后才能将该机制用于正式流量统计。尚未实现 OxiDNS 定时调度、指标聚合、前端、HA 和 Docker；NetFlow 累计连接快照不能直接作为时段流量。当前目录仍不是可部署成品。

同步每次会回看此前 5 分钟，以降低上游写入延迟导致的漏采概率；但重扫并不证明上游历史已经完整。为避免把不完整证据误当成可靠匹配，分析器默认返回 `dns_completeness_unverified`；只有在来源完整性经过验证并显式提供该条件后，才运行归因匹配。此限制当前不会自动解除。

## 独立 IPFIX 接收器进度（用户授权例外后）

用户已明确允许未来增加独立的 RouterOS IPFIX 导出目标；现有导出目标必须保留。V2 已复制上游 Apache-2.0 解码和归一化代码到独立模块，并保留许可及其脱敏抓包测试；原采集器源码和运行环境未修改。V2 接收器可通过可选 Compose 覆盖文件配置独立 UDP 端口和导出源白名单，数据保存至独立数据库。

已实现同一数据报的事务去重、IPFIX 序列范围重叠拒绝、字节溢出检查和按接收小时聚合。按接收小时计量是导出观测口径，不等同准确的逐分钟发生时间。源设备漏包、缺模板、硬件卸载、FastTrack 和采样均可能造成覆盖不足；不可声称抓到全部真实流量。

接收时在独立副本中解码并计算时钟，仅在数据库事务成功后提交状态；已存在模板的变更或撤销会被保守拒绝。进程重启后等待新模板，不使用缺少会话身份的旧缓存。未知模板、选项模板、不完整数据以及多余尾部会被拒绝。

后续会话校验以导出源、观测域和可验证的设备启动时间隔离序列范围，消除重复并有界接受乱序，在证据充分时可接受重启和 32 位序列回绕。缺少启动信息、模板不一致、序列范围重叠或超出乱序窗口的数据会拒绝计入。真实设备覆盖率仍需现场核验。

字节接口根据独立 IPFIX 的接收时间累计观测量。应用归因依赖有效时间范围内的 DNS 证据，默认全部计入未知，并给出原因。真实录制源的证据完整性和分应用覆盖尚待验证。

## 部署配置验收

基础配置使用回环地址发布 Web，IPFIX 覆盖文件默认也只在回环地址发布 UDP。Compose 要求应用密码，启用接收器时还要求显式配置导出源和局域网 CIDR。容器以非 root 用户运行，移除全部 Linux capabilities，根文件系统只读，通过专用数据卷和临时文件系统写入。

基础配置和 IPFIX 覆盖配置已通过 Windows 上独立 Compose CLI 的静态校验，Linux amd64 静态 Go 产物已构建。Windows 原生进程使用独立临时库完成 HTTP 和脱敏抓包 UDP 重放验收。观察及未知字节各为 249,974,751，归因为零，重放后字节数未增加。GitHub Actions 上 Linux 镜像构建、非 root 容器启动、数据卷写入、健康与认证检查通过。真实 OxiDNS 的认证和样本窗口分页已核验；RouterOS 现场端到端收包及持续 DNS 完整性仍需验证。
